**Основание:** [архитектура v0.2 — проект](03-architecture-v0.2-draft.md), [требования v0.2 — проект](02-requirements-v0.2-draft.md).

## 1. Цель

Реализовать SDK-независимую основу модульной системы видеоаналитики с единой подачей кадров, независимым включением/выключением детекторов, маршрутизацией результатов и измерением затрат CPU/RAM/FPS.

**В рамках #5 реализуются инфраструктура и тестовые детекторы-заглушки, но не сами алгоритмы проникновения, дыма и смещения** (для них существуют #6–#8).

Целевые физические пороги 0,5 м² / 20% / 5 см нельзя объявить достигнутыми по результатам этой задачи.

## 2. Технический подход

**Рабочее предложение:** C++17 и CMake для ядра; тонкий адаптер к нативному C API SG2002/MMF; минимальное количество внешних зависимостей. Язык/сборка ещё требуют проверки установленного toolchain на устройстве — это **предложение, не утверждение**.

Модульный монолит: один процесс, один владелец видеоподсистемы, отдельные компоненты с чёткими интерфейсами. Начальный режим — один поток получения кадров и управляемое последовательное исполнение детекторов. Параллелизм добавлять только после измерений.

**Схема источников:**

```text
GC4653 → [SG2002 MMF adapter] → LiveFrameSource ───┐
                                                      ├─> IFrameSource
Dataset file / test generator → DatasetFrameSource ──┘        │
                                                              ↓
                                                        Dispatcher
                                                              ↓
                                                  DetectorManager
                                                  /      |       \
                                               dummy-A dummy-B dummy-C
                                                  \      |       /
                                                   DetectionResults
                                                          ↓
                                                   EventManager
                                                          ↓
                                                JSONL + Diagnostics
```

**Уточнение относительно v0.2:** офлайн-источник кадров не должен проходить через VI/ISP/VPSS. Аппаратный MediaAdapter принадлежит только `LiveFrameSource`. Общий контракт начинается с `IFrameSource`.

## 4. Контракты и инварианты

### 4.1. `FrameLease` / `FrameView`

`FrameView` содержит ID, монотонную метку кадра, размер, stride, пиксельный формат, ROI, идентификатор калибровки и только доступ к данным в пределах времени жизни `FrameLease`.

- При выходе из обработки буфер освобождается **ровно один раз**.
- Детектор не хранит невалидный указатель после возврата.
- Данные кадра рассматриваются как read-only; изменения только в собственном буфере детектора.
- Если SDK не обеспечивает безопасного разделения буфера, использовать ограниченные копии.
- Объём кадровых очередей конечен; передавать последние кадры вместо накопления отставания.

### 4.2. `IFrameSource`

Методы: `open(config)`, `next_frame(timeout)`, `close()`. Источники: `DatasetFrameSource`, затем `LiveFrameSource`. При EOF, timeout и аппаратной ошибке — разные диагностические статусы.

### 4.3. `IDetector`

Методы: `configure()`, `start()`, `process(FrameView)`, `stop()`, `status()`. Детектор не открывает камеру, не пишет сетевые сообщения напрямую и не управляет другими детекторами.

### 4.4. `DetectorManager`

Состояния `DISABLED`, `INITIALIZING`, `WARMING_UP`, `RUNNING`, `STOPPING`, `ERROR`.

- Включение конкретного модуля не прерывает остальных.
- При выключении перестают приходить новые кадры; выполняется завершение текущей обработки с учётом таймаута, освобождаются ресурсы детектора.
- Повторное включение может заново прогревать фоновую модель.
- Падение детектора по ошибке возвращаемого статуса не останавливает другие модули; краш всего процесса не считается изолированным.
- Все 8 комбинаций трёх флагов включения поддержаны логически. Их производительность проверяется позднее.

### 4.5. `EventManager`

Результаты детекторов преобразуются в типизированные события `start/update/end` и журналируются в JSONL. В событии минимум: `event_id`, `event_type`, `detector_id`, `frame_id`, `timestamp`, `region_id`, `measurements`, `calibration_id`, признак валидности измерений. Физические единицы не утверждать без калибровки.

## 5. Порядок реализации внутри Issue #5

**A. Предварительная инвентаризация**
- Подтвердить OS, CPU ABI, toolchain, версию SDK, интерфейсы GC4653, MMF/VI/VPSS, доступность Y-plane и обязательные вызовы release.
- Зафиксировать в `docs/platform-inventory.md` реально проверенные возможности; неизвестное не маскировать предположениями.

**B. SDK-независимое ядро (можно готовить без устройства)**
- Объявить структуры кадров, интерфейс источников, результаты и события.
- Реализовать генератор/источник тестовых записанных кадров.
- Добавить `DummyDetector` и менеджер независимых жизненных циклов.
- Реализовать ограниченную диспетчеризацию, журнал JSONL и диагностику.
- Добавить конфигурацию с пояснениями каждого параметра и его единиц измерения.

**C. Адаптер SG2002 (после инвентаризации)**
- Реализовать единоличное владение и инициализацию видеоподсистемы.
- Получать кадры GC4653 и согласованный формат для ядра.
- Корректно освобождать кадры, закрывать и повторно открывать источник.
- Проверять отсутствие утечек и накопления MMF/VB при многократных стартах и остановках.

**D. Интеграция и проверки**
- Прогонять те же DummyDetector через Dataset и LiveFrameSource.
- Проверить горячее включение/выключение трёх независимых модулей.
- Проверить порядок событий, наблюдаемость ошибок и закрытие ресурсов.
- Зафиксировать фактические метрики, не назначая заранее неподтверждённый FPS.

## 6. Тесты и критерии приёмки

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| T01 | В источнике 100 кадров, один DummyDetector | Каждый обработанный кадр имеет корректный ID и метку; нет повреждения буфера |
| T02 | Три выключенных детектора | 0 вызовов `process`; источник может оставаться запущенным |
| T03 | Все 8 комбинаций из 3 детекторов | Обработка только в включённых модулях |
| T04 | Выключить один модуль во время работы остальных | Остальные продолжают получать кадры |
| T05 | Повторно включить модуль | Корректная инициализация и прогрев |
| T06 | Медленный тестовый модуль | Очередь остаётся ограниченной; пропуски измеряются |
| T07 | Источник завершён / timeout / ошибка | Диагностика различает ситуации; без зависаний |
| T08 | Сгенерировать события `start/update/end` | Валидные JSONL-записи с полями и единицами |
| T09 | Запуск/остановка видеотракта N раз | Без утечек и двойного release; N задаётся в методике теста |
| T10 | Прогон тех же кадров через два источника | Сопоставимые результаты заглушек по кадрам, без требования равенства времени CPU |

Тесты T01–T08 можно выполнить без физической платы. T09 и аппаратная часть T10 требуют SG2002 и рабочей камеры.

## 7. Ограничения, зависимости и риски

- **#3 Требования** и **#4 Архитектура** ещё открыты. В #5 можно вести подготовку SDK-независимого ядра, но окончательный контракт и релиз блокируются согласованием #3/#4.
- Проверка реальной версии SDK, ABI, MMF/VI/VPSS и release-семантики обязательна до интеграции камеры.
- Пороговые условия детекции, точные частоты/разрешения и расписание модулей уточняются после испытаний.
- `events.jsonl` — минимальный локальный вывод; RTSP/HTTP/MQTT не включать автоматически до решения о требуемых интерфейсах.
- В целях экономии RAM избегать тяжёлого OpenCV там, где достаточно явной работы с Y-каналом; окончательный выбор после замеров.

## 8. Definition of Done

- Исходники собираются для host и целевой ABI (после появления проверенного toolchain).
- SDK-независимые компоненты покрыты воспроизводимыми тестами T01–T08.
- Камера GC4653 подключена через `LiveFrameSource`, проверен повторный старт, выполнены аппаратные тесты T09–T10.
- Конфигурация документирована; нет скрытых значений и обязательной одновременной обработки.
- Есть руководство сборки, запуска и журнал фактической производительности.
- Условия работы и API ядра согласованы с #3 и #4.

**Не считается выполнением #5:** реализация, обучение или тестирование самих алгоритмов #6–#8.
