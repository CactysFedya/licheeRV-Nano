# Проект архитектуры v0.2 — модульная видеоаналитика на LicheeRV Nano

**Статус:** проект для технического согласования, не завершённая реализация.  
**Платформа:** SG2002, 256 МБ RAM, GC4653, стационарная установка в помещении.  
**Документы:** [исследование](01-research-algorithms.md) · [требования v0.2 (проект)](02-requirements-v0.2-draft.md) · [архитектура v0.1](03-architecture-v0.1.md) · [Issue #4](https://github.com/CactysFedya/licheeRV-Nano/issues/4).

## 1. Цель и границы

Спроектировать один исполняемый модуль классической видеоаналитики с независимыми детекторами:
- **intrusion** — проникновение движущегося объекта (цель: площадь от 0,5 м²);
- **smoke** — появление дыма (цель: площадь от 0,5 м², контраст от 20%);
- **displacement** — смещение протяжённого объекта (цель: от 5 см).

Эти физические пороги пока **не подтверждены**. Геометрия помещений, дальности, методика измерения контраста и требования к ложным тревогам остаются открытыми в Issue #3. На этапе архитектуры не пишем код детекторов и не выдаём расчётные характеристики за измеренные.

## 2. Архитектурное решение (предлагается утвердить)

**Модульный монолит:** один Linux-процесс, один владелец аппаратного видеоустройства, подключаемые детекторы через типизированный интерфейс. Отдельные процессы для каждого детектора пока не нужны — на плате всего 256 МБ RAM. Исключения и ошибки модулей обрабатываются по возможности, но один процесс не обеспечивает полной изоляции аварий и ошибок памяти.

```text
 GC4653 / recorded dataset
          │
      FrameSource
       (live/file)
          │
     Media Adapter            [SG2002: VI → ISP → VPSS, доступность API проверить]
          │
     Frame Dispatcher ────────→ optional video stream / recorder
          │
     Detector Manager  ←────── configuration / control
     /     │      \
intrusion smoke  displacement  (only enabled detectors process frames)
     \     │      /
        Results
          │
      Event Manager ──────────→ JSONL / future transport
          │
     Metrics / Diagnostics
```

**Не делать:** не создавать независимую камеру/VI для каждого детектора; не копировать полный кадр каждому модулю без необходимости; не строить бесконечные очереди; не требовать запуска всех трёх алгоритмов одновременно.

## 3. Компоненты и ответственность

| Модуль | Назначение | Не отвечает за |
|---|---|---|
| `FrameSource` | Выдаёт последовательность кадров с временными метками и идентификаторами | Алгоритмы детекции |
| `LiveCameraSource` | Управляет видеоадаптером/запуском и остановкой GC4653 | Детекторы |
| `DatasetSource` | Подаёт подготовленные кадры и исходные временные метки | Работа с MIPI |
| `MediaAdapter` | Изолирует SG2002 MMF/VI/ISP/VPSS, pixel formats, ROI, владение буферами | Бизнес-логика |
| `FrameDispatcher` | Направляет кадры только активным потребителям с backpressure | Вычисление тревог |
| `DetectorManager` | Конфигурация, enable/disable, lifecycle, частота и ошибки детекторов | Физическая калибровка |
| `Detector` | Анализ кадра, поддержка внутреннего состояния и результаты | Сетевые сообщения |
| `EventManager` | Нормализация, смена состояний событий, логирование, дедупликация | Алгоритм детекции |
| `CalibrationStore` | Данные сцены, плоскости, масштаба и версия эталона | Автоматическое знание глубины |
| `Diagnostics` | FPS, задержки, очереди, CPU/RAM, ошибки и повторный старт | Отслеживание истинных событий |

## 4. Контракты интерфейсов (концептуальные, язык реализации ещё не выбран)

### 4.1 `FrameView`

Не владеющее представление доступной области пикселей. Минимальные поля:
- `frame_id: uint64`; `capture_time_monotonic_ns: uint64`;
- `wall_time_utc: optional` (для внешних событий, не для вычисления задержек);
- `width, height, stride_bytes, pixel_format`;
- `roi_in_sensor_coords`, `sensor_id`, `calibration_id`;
- `data_handle` и `lease` с **явным сроком жизни**;
- `source_type: live | dataset`.

**Важно:** `FrameView` допустим только до завершения предоставленного `lease`; детектор не удерживает указатель после возврата из обработки. Если доступ к аппаратному буферу не может быть безопасно разделён — адаптер предоставляет ограниченную копию/вторичный буфер. Должна существовать одна ответственная точка освобождения MMF/VB-ресурса.

### 4.2 `FrameSource`

```text
open(config) -> Status
next_frame(timeout) -> FrameLease | EndOfStream | Error
close() -> Status
```

Датасет и камера должны давать одинаковый `FrameView`; детектор не знает, откуда получен кадр. Параметры воспроизведения: исходная частота/временные метки либо максимальная скорость, выбором теста.

### 4.3 `Detector`

```text
id() -> DetectorId
configure(DetectorConfig) -> Status
start(Context) -> Status
process(FrameView) -> DetectionResult[]
stop() -> Status
status() -> DetectorStatus
```

Интерфейс является **контрактом**, а не готовым C++ API. `Context` может предоставлять конфигурацию, метрики и калибровку; детектор не должен напрямую управлять камерой или EventManager. `process` не вызывается при `DISABLED`.

### 4.4 `DetectionResult` и `Event`

Внутренний результат включает `detector_id`, `frame_id`, `capture_time_monotonic_ns`, `region`, `measurements`, `calibration_id`, `quality_flags`. Его обработка в `EventManager` создаёт событие `start / update / end` с `event_id`, `event_type`, меткой времени и измеренными величинами.

- Для площади и смещения обязательны **единицы измерения** и признак `measurement_valid`.
- События при отсутствии корректной калибровки не должны выдавать значения в м² или см как достоверные.
- `score` — только алгоритмическая оценка, не вероятность, пока не выполнена калибровка.
- Переходы `start/update/end` и дедупликация событий конфигурируются и тестируются отдельно.

## 5. Жизненный цикл и независимое управление

```text
DISABLED
  ↓ enable
INITIALIZING → WARMING_UP → RUNNING
  ↑                                │
  └──────── stop ← STOPPING ← disable
                      ↑
             ERROR / DEGRADED
```

- `enable` запускает конкретный детектор, при необходимости заново строит фон/эталон.
- `disable` отменяет ожидающие задания, ждёт завершения текущего вызова (с ограничением времени), освобождает состояние и память, прекращает получение кадров **этим модулем**.
- Остановка детектора не выключает общий видеозахват, если он нужен другим потребителям.
- Ошибка одного детектора не должна автоматически останавливать остальные; аппаратный сбой общего источника кадров объявляется системным.
- Любая комбинация `000…111` трёх флагов доступна в конфигурации; реальная производительность для каждой конфигурации проверяется позднее.
- `WARMING_UP` обязателен там, где алгоритму нужен временной фон или эталон; состояние и факт прогрева фиксируются.

## 6. Видеоконвейер и планировщик

Первый вариант — отдельный **поток захвата** и один **управляемый поток обработки** в одном процессе. Параллельное исполнение детекторов или очереди на каждый модуль — только после измерений.

1. Камера генерирует кадр с меткой захвата.
2. `MediaAdapter` выдаёт `FrameLease` и согласованный формат.
3. `FrameDispatcher` проверяет список активных детекторов, их `analysis_fps`, нужный формат и ROI.
4. Если обработка ещё занята, новые или старые кадры пропускаются по заданной политике `latest-frame`; кадры не накапливаются без границ.
5. Исполнение детектора возвращает результаты и освобождает `lease`.
6. `EventManager` формирует события, а `Diagnostics` фиксирует задержку, очередь, пропуски.

Детекторы могут иметь **разные входные разрешения**: предполагаемый базовый Y-кадр 640×360 или 320×180 для проникновения/дыма; ROI с большей детализацией для смещения. Это *варианты*, не зафиксированные рабочие режимы: доступные каналы VPSS, IVE и число копирований проверяются на целевом SDK. При недостатке аппаратных выходов допускается программное масштабирование с учётом измеренной нагрузки.

**Временные отметки:** задержку считать по монотонному времени (не по UTC); для датасетов отдельно хранить время кадра и время обработки. Политика сброса кадров не должна создавать ложное ощущение высокой частоты детекции.

## 7. Память и освобождение ресурсов

- Учитывать общие 256 МБ RAM: ОС, ISP/MMF/VB, видеобуферы и пользовательский процесс делят память.
- Пулы VB и количество кадров **не назначать жёстко** без анализа реального SDK.
- Избегать конвертации всех кадров в RGB; работать с яркостной плоскостью, когда это допускает алгоритм.
- Ограничить очередь, временные окна, копии ROI, модели фона и журнальные буферы; предусмотреть диагностику пикового потребления памяти.
- Сохранить **один владеющий компонент** для `init/shutdown` видеоподсистемы; аппаратные буферы возвращать точно один раз.
- Контрольная проверка на будущем этапе: запуск → остановка → повторный запуск **без перезагрузки платы**.
- Известный внешний отчёт о возможном неполном освобождении VB на одной прошивке: [Sipeed LicheeRV-Nano-Build issue #833](https://github.com/sipeed/LicheeRV-Nano-Build/issues/833). Это **риск**, не доказательство неисправности нашей сборки.

## 8. Калибровка и особенности детекторов

| Детектор | Планируемые входы | Хранимое состояние | Внешние условия |
|---|---|---|---|
| Проникновение | Y / ROI, правила зоны | Фоновая модель, объекты, траектории | Площадь 0,5 м² требует согласованной геометрии |
| Дым | Y / при необходимости цвет и временные признаки | История и эталон фона | Определение контраста 20% и площади ещё не согласовано |
| Смещение | Детальный ROI, эталонные признаки | Эталон, реперы, версия калибровки | Пересчёт пикселей в 5 см только с масштабом в контрольной плоскости |

Алгоритмические данные детекторов разделены: отключение проникновения не ломает детекцию дыма и смещения. Общими являются только кадры, инфраструктура и дополнительные универсальные операции обработки.

## 9. Конфигурация (иллюстративная схема, не готовый формат)

```toml
[camera]
source = "gc4653"          # либо "dataset"

[pipeline]
analysis_size = "640x360" # предварительно, доступность проверить
queue_policy = "latest"

[detectors.intrusion]
enabled = true

[detectors.smoke]
enabled = false

[detectors.displacement]
enabled = true

[events]
output = "jsonl"
```

Для каждого ключа в реализации обязателен комментарий о назначении и единицах измерения, если они применимы. При ошибке конфигурации система выдаёт диагностическое сообщение, а не молча применяет неизвестное значение. Горячая перенастройка видеопотока и горячее включение модулей — **разные** операции; второе не должно зависеть от первого.

## 10. Проверка архитектуры без реализации детекторов

Документ считается готовым к утверждению, если:
- определены роли модулей, направление вызовов и контракты;
- выключенный детектор не получает кадры и не выполняет обработку;
- все 8 комбинаций включённости 3 детекторов предусмотрены;
- live и dataset используют единый `FrameSource`;
- ограничения очередей, срок жизни кадров и порядок освобождения ресурсов описаны;
- калибровка физического масштаба отделена от алгоритмов и имеет валидность;
- есть метрики и политика ошибок;
- спорные вопросы SDK и условий эксплуатации явно отмечены как зависимости.

**Вне текущего этапа:** реализация, экспериментальное подтверждение FPS, точности порогов и потребления памяти.
