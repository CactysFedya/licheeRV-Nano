# Требования к системе видеоаналитики — проект v0.2

**Платформа:** LicheeRV Nano (SG2002), камера GC4653  
**Область применения:** стационарная камера внутри помещений  
**Статус:** проект для согласования. Неподтверждённые показатели не следует трактовать как гарантии изделия.  
**Предыдущая версия:** [v0.1](02-requirements-v0.1.md) · [Epic #1](https://github.com/CactysFedya/licheeRV-Nano/issues/1) · [Issue #3](https://github.com/CactysFedya/licheeRV-Nano/issues/3)

## 1. Термины статуса

- **Зафиксировано** — явно согласовано в проектной постановке.
- **Предложено** — рабочее инженерное допущение; требуется согласование.
- **Открыто** — нельзя достоверно нормировать без решения о сценариях эксплуатации.

## 2. Границы проекта

| ID | Требование | Статус |
| --- | --- | --- |
| SYS-01 | Использовать LicheeRV Nano / SG2002, GC4653 и классические методы CV без нейросетей | Зафиксировано |
| SYS-02 | Стационарная камера внутри помещений | Зафиксировано |
| SYS-03 | Независимое включение и выключение каждого детектора без перезапуска всего приложения | Зафиксировано |
| SYS-04 | Допускать включение любой комбинации из трёх детекторов; выключенный детектор не анализирует кадры | Зафиксировано |
| SYS-05 | Сохранять диагностические измерения FPS, загрузки CPU, использования RAM, задержек и ошибок | Предложено |
| SYS-06 | Поддерживать единый формат событий и использование подготовленных видеоданных вместо живой камеры | Предложено |

Система обеспечивает алгоритмические события видеоаналитики; видеодетекция дыма сама по себе **не заменяет сертифицированные средства пожарной сигнализации**.

## 3. Детектор проникновения

| ID | Требование | Статус |
| --- | --- | --- |
| INTR-01 | Обнаруживать проникновение в заданную охраняемую область движущегося объекта площадью не менее **0,5 м²** | Зафиксировано |
| INTR-02 | Конфигурировать охраняемую зону и выдавать событие с её идентификатором и временем | Предложено |
| INTR-03 | Подтверждать наличие движения во времени, не считать единичный скачок яркости достаточным основанием | Предложено |

**Требует решения:** «площадь объекта» — реальная площадь поверхности, площадь видимой проекции на калиброванную плоскость или иной критерий? Одна монокулярная камера не определяет фактическую площадь произвольного 3D-объекта из изображения без дополнительных предположений.

## 4. Детектор дыма

| ID | Требование | Статус |
| --- | --- | --- |
| SMK-01 | Обнаруживать появление дыма площадью не менее **0,5 м²** при контрасте от **20%** | Зафиксировано |
| SMK-02 | Формировать событие и, при возможности, область появления дыма | Предложено |
| SMK-03 | Учитывать помехи: пар, пыль, тени, изменение экспозиции и освещения | Предложено |

**Предложение по измерению контраста для дальнейшего согласования:** относительное изменение локальной яркости относительно эталонного фона по формуле `C = abs(Y_current - Y_background) / max(Y_background, ε)`. Выбор статистики по области (среднее, медиана, процентиль), `ε`, режим автоэкспозиции и допустимая погрешность пока не установлены. Указанная формула — **не утверждённая интерпретация** исходных 20%.

**Требует решения:** физическое определение «площади дымовой струи», условия формирования эталона, освещённость, цвет и плотность дыма, допустимый уровень ложных тревог и задержка срабатывания.

## 5. Детектор смещения

| ID | Требование | Статус |
| --- | --- | --- |
| DISP-01 | Обнаруживать смещение протяжённого объекта от **5 см** в плоскости, перпендикулярной оптической оси камеры | Зафиксировано |
| DISP-02 | Сравнивать текущее положение с эталоном и выдавать событие с измеренным смещением и единицами | Предложено |
| DISP-03 | Использовать калибровку масштаба/геометрии и контролировать стабильность самой камеры | Предложено |

Для проверки на расстоянии задаётся плоскость объекта и метрический масштаб (реперы или калибровочная мишень). Рекомендуемые точки будущей проверки: 0, 3, 5, 7, 10 см — **не нормативные допуски**.

**Требует решения:** какие протяжённые объекты контролируем; рабочая дистанция; размеры и ориентация; уровень вибрации; критерий сброса/обновления эталона.

## 6. Предлагаемый формат события

Детектор не должен зависеть от способа передачи события наружу. Минимальный проектный контракт:

```json
{
  "event_type": "intrusion",
  "detector_id": "intrusion_1",
  "timestamp": "ISO-8601",
  "frame_id": 123,
  "state": "start",
  "region_id": "zone_a",
  "measurements": {},
  "calibration_id": null
}
```

Допустимые значения `state`: `start`, `update`, `end`. Для событий с физическими величинами передавать единицы измерения и признак валидности калибровки. Точная схема, журналирование и транспорт утверждаются при проектировании архитектуры.

## 7. Методика будущей проверки

1. **Проникновение:** сценарии входа/выхода из зон, серия объектов с известными габаритами и дистанциями, отдельные негативные примеры с изменением освещения.
2. **Дым:** подготовленные видео и отдельные контролируемые сценки с известным фоном, установленной методикой измерения контраста и видеозаписями помех.
3. **Смещение:** контролируемые перемещения от эталонного положения на фиксированной дистанции, проверка в нескольких точках и с повторной калибровкой.
4. **Интеграция:** включение и выключение отдельных модулей, работа 1/2/3 детекторов, CPU/RAM/FPS, потери кадров, задержки, длительная стабильность.

Предлагаемые метрики: доля верно обнаруженных событий, частота ложных тревог на час наблюдения, задержка обнаружения, абсолютная ошибка оценки смещения в сантиметрах. **Целевые значения не установлены.**

## 9. Условия завершения Issue #3

Задача может быть закрыта только когда для O-01…O-07 согласованы решения либо явно зафиксирована ограниченная область применения с обоснованием. До этого данный документ — **рабочая спецификация, а не утверждённое ТЗ**.

Далее: актуализировать архитектуру [v0.1](03-architecture-v0.1.md) в [Issue #4](https://github.com/CactysFedya/licheeRV-Nano/issues/4), не подменяя проверку реальных порогов теоретическими оценками.
